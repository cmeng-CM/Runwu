## 1. 总体结论

**有条件可实施。**

方案的主干是合理的：复用同一条输入快照与防抖链路、复用 `.realtime` 浮窗体系、新增独立校准状态机与协调器、在 `LLMModelRouter` 内增加一个不走翻译提示词的结构化任务；这些选择与现有代码的边界基本相容，也没有引入不必要的第二套输入/浮窗架构。

但 v1.1 当前不能直接进入实施，原因是若干**核心机制在正文中没有落到可执行的程度，甚至与现有代码事实相反**：

1. 校准路由在 `InputCoordinator` 的源语言硬过滤处就会被丢弃，设计只写了“携带路由标记”，没有写要替换这个门槛；按现状实现，默认“中→英”配置下英文句永远到不了校准。
2. 若按 4.1 的“CalibrationState = 无 Han 且含 Latin”实现，源语言为英/法/德/西时英文句会同时满足翻译与校准，源语言为日/韩/俄时 Kana/Hangul/Cyrillic+Latin 混排句也会同时满足两路；这与 D-C2“翻译优先”、A4“源=英不出校准卡”以及 D-C8 的“英文→校准候选”互相冲突。
3. 校准卡的尺寸、滚动、拖选、拖拽、缩放没有可执行的量高与交互契约；正文声称“按 origin 驱动、与内容形态无关”，但拖选/hover/拖拽是视图层机制，不是 origin 层机制。现有代码注释和测试已经记录了 `NSHostingView.fittingSize` 上屏后塌缩、面板矮于内容会压住输入行的事故。
4. 解码宽容规则会在 `verdict=minor/major` 但缺少 `issues`/`corrected` 时把结果降为 `good`，这违背 D-C4“失败不冒充校准结果”的原则，也会把“表意有误”显示成“表达到位”。
5. 回译到底回译**原句**还是**修正句**没有定义；这是“是否表达本意”的核心语义，不能留给实现者猜。
6. 校准用的 `LLMModelRouter` 实例由谁创建、如何随设置 reconfigure、请求是否经过 `configurationReady` 屏障均未定义；设置变更后可能出现静默丢弃或旧配置请求。
7. 失败提示复用了翻译失败通道，但 `presentFailure` 需要 `TranslationBackend`、提示窗标题固定为“实时翻译”，且没有“新请求/成功时清除校准失败”的契约；会出现失败提示标题错误、失败提示与新卡并存、或校准失败覆盖翻译失败。

这 9 项属于**阻塞缺陷**。另有 2 项必须先由用户确认的产品口径（不完整句是否校准、拉丁源配置下“翻译优先”是否仍符合用户的两模式心智），见 Q-01、Q-02。修订后可按第 8 章顺序实施；在此之前，“全文可实施”的文档状态不成立。

## 3. 端到端机制走查

以下按“操作前状态 → 操作 → 操作后状态 → 约束是否成立”走查。所有涉及代码的行号均为当前基线 `4815b09`。

### 3.1 中文句 → 翻译（回归路径）

- 操作前：`realtime.sentence = nil`，无卡。
- 操作：输入中文句，`InputCoordinator.emit` 的 `detector.contains(sentence, language: .chinese)` 通过（`Input.swift:196`），回调 `AppState.translate`。
- 操作后：`realtime.beginRequest` 成功，翻译卡出现。
- 结论：**成立**；开关关闭时这条路径必须保持零变化。注意 `InputCoordinator` 的回调签名一旦加入路由标记，既有测试闭包需要机械适配（B-02、D-12）。

### 3.2 英文句 → 校准（核心路径）

- 操作前：开关开、源语言中文、无卡。
- 操作：输入英文句，停顿 450ms。
- 现状代码：`InputCoordinator.emit` 在 `Input.swift:196` 先执行 `guard detector.contains(sentence, language: sourceLanguage)`；源语言中文时纯英文句不通过，直接 `sentence skipped reason=sourceLanguageMismatch` 返回，**`onSentence` 根本不会被调用**。
- 设计正文：2 章把“语言过滤丢弃点”归到 `RealtimeTranslationState.update`（Models.swift:194-204），改造影响表只写 `InputCoordinator` “发射时携带路由标记（翻译/校准），时机机制不变”（文档 59 行），没有写要替换 `Input.swift:196` 的硬过滤。
- 结论：**不成立**。按 v1.1 的改造清单实现，校准支路不会触发。修复见 B-02。

### 3.3 英文句 → 校准（假设已替换 InputCoordinator 门槛）

- 操作前：源语言中文，`realtime.sentence=nil`。
- 操作：英文句上屏，`CalibrationState.update` 按“无 Han 且含 Latin”接受，`beginRequest` 发令牌。
- 操作后：请求发出，结果返回后出卡。
- 结论：**在源语言=中文时成立**；但同一过滤器在源语言=英/法/德/西时会与翻译过滤器同时接受同一句（B-01）。

### 3.4 中文卡 → 英文句切换

- 操作前：翻译实时卡显示，`realtime.sentence = 中文句`。
- 操作：删句改打英文。
- 现状：`realtime.update` 抽到英文句，`LanguageTextDetector.contains(..., .chinese)` 为 false → `sentence=nil`，与旧值不同 → 返回 true → `clearRealtimePresentation()` → `overlay.hideRealtime()`（App.swift:617-629、Overlay.swift:1449-1451），翻译卡被移除；校准新请求发出。
- 结论：**成立**，且 `hideRealtime` 对钉住卡有 `detached` 豁免。设计 4.1 场景 1 的描述正确。

### 3.5 英文卡 → 中文句切换

- 操作前：校准卡显示，`realtime.sentence=nil`（英文被过滤）。
- 操作：输入中文句。
- 现状：`realtime.update` 抽到中文句，从 nil 变为非 nil → 返回 true → `clearRealtimePresentation()` → `hideRealtime()` 会隐藏**所有**未钉住的 `.realtime` 卡，包括校准卡；随后翻译请求出卡。
- 结论：**机制上成立**，但设计只写了“showing + 用户打中文句 → 卡隐藏（clearRealtimePresentation 语义）”，没有说明这是复用 `hideRealtime` 的全局清除；校准卡与翻译卡共用 origin，未来若想只清一类卡，现有 API 做不到。应把这一依赖写明，避免实现者误以为需要按类型分卡（B-03 的边界）。

### 3.6 英文卡 → 继续改英文句（关键缺口）

- 操作前：校准卡显示（句子 A），`realtime.sentence=nil`。
- 操作：继续输入，句子变成 B。
- 现状：`realtime.update` 对 B 仍返回 `sentence=nil`；`self.sentence == next`（nil == nil）且 session 未变 → 返回 false，**不会触发 `clearRealtimePresentation`**。若 `CalibrationState.update` 返回 true，但 AppState 没有对应的“清校准展示”函数，旧卡 A 会保留到 B 的 LLM 结果返回（2–6 秒）后才被新卡替换。
- 结论：**不成立**。设计 4.1 状态表只有 `pending(v1) → 句子变化 → pending(v2)`，没有 `showing → 新句 → 旧卡隐藏` 的转换，也没有定义 `clearCalibrationPresentation`。修复见 B-03。

### 3.7 空字段 / 失焦 / 暂停 / 设置变更

- 操作前：校准请求在途或校准卡显示。
- 操作：清空输入框 / 切窗口 / 菜单栏暂停 / 改源语言或模型。
- 现状：`onEmpty`（App.swift:237-240）→ `invalidateRealtime` → `realtime.invalidate` + `clearRealtimePresentation`；`onFocusChanged`（213-216）→ `invalidateRealtime` + `input.reset()`；`toggle()`（458-481）→ `applyTranslationSettings()`，其中 `invalidateRealtime(clearAnchor: true)`；`applyTranslationSettings` 同样只处理 `realtime`/`coordinator`/`clipboardCoordinator`。
- 缺口：**没有 `CalibrationState.invalidate`，也没有 `CalibrationCoordinator.cancel`**。清空字段后，之前发出的校准请求仍可能通过 `CalibrationState.accepts`，在空字段上出卡；失焦/暂停/设置变更同理。设计 4.1 写“复用既有失效路径”，但既有路径只清 `realtime`，这句话在代码上不成立。
- 结论：**不成立**。修复见 B-03。

### 3.8 失败路径

- 操作前：校准请求在途，或旧校准卡显示。
- 操作：所有模型失败/未配置模型。
- 设计：5.2 “AppState 走 `presentFailure` 独立提示，不出卡”。
- 现状：`presentFailure(_:backend:origin:key:session:)` 需要 `TranslationBackend`（App.swift:932-946）；内部 `overlay.hideRealtime()` 会移除未钉住的 `.realtime` 卡，然后设置 `realtimeFailure` 并调用 `liveFailureNotice.show`；`TranslationFailureNotice` 的标题固定为“润物 · 实时翻译”（1016-1022）。`TranslationFailureMessage.text(for:backend:language:)` 没有“校准”分支（Models.swift:626-653）。
- 结论：**不完整**。会出现：失败提示标题写成“实时翻译”；校准失败占用翻译失败槽，下一次翻译请求开始时的 `clearFailure(realtime: true)` 会把校准失败一并清掉；校准成功时没有清失败提示的契约；钉住的旧校准卡不会被 `hideRealtime` 移除，可能出现“旧卡 + 新失败提示”。修复见 B-09。

### 3.9 卡尺寸、滚动、拖选、拖拽

- 操作前：无卡；校准结果含 1–10 条 issues。
- 操作：出卡；拖动；滚轮；拖选；拖底边缩放；钉住。
- 现状：`installContent` 用 `OverlaySizing.textHeight` 计算 `naturalText`，再 `OverlaySizing.plan` 得到 `textHeightLimit`/`cardHeight`，写入 `entry.plannedCardHeight`；`relayout` 取 `max(fitting.height, plannedCardHeight)`（Overlay.swift:1087-1101、1468-1471）。代码注释明确记录：`NSHostingView.fittingSize` 上屏后会塌缩（279 字符译文只报 110 点），面板矮于内容会画出面板之外并压住输入行；`OverlayCoordinatorRenderingTests.testCardPanelIsNeverShorterThanItsMeasuredText` 是专门守这条约束的回归测试。
- 设计 4.3：校准卡“不做纯文本量高，依赖 NSHostingView fittingSize，面板高度沿用 max(fittingSize, 预算高度) 与 cardHeightLimit（240…460/0.6 屏）滚动策略”。
- 缺口：没有定义“预算高度”怎么来；如果 `plannedCardHeight` 为 nil，`relayout` 只剩 `fitting.height`，正是已知会塌缩的值；`cardHeightLimit` 是 `OverlayCoordinator` 的私有函数，校准卡没有对应的自然高度/滚动阈值计算；`chrome`（头部/内边距）仍按翻译卡的 `chromeHeight()` 或空文本宿主测量，校准卡头部有徽标、无服务菜单，尺寸不同；没有长 issues 列表的滚动阈值。
- 结论：**不成立**。修复见 B-04。

### 3.10 拖选与 hitTest

- 现状：`WindowDragCatcherView.hitTest` 在 `selectableBodyTop` 为 nil 时，除头部按钮区/缩放把手外整卡返回自身，即整卡可拖动（Overlay.swift:103-128）；`bodyEntry` 只在 `selectableBodyTop > 0` 时把屏幕点判为“正文区”（1285-1296）；`copySelection` 依赖该判断。
- 设计 4.3：校准卡“正文区 `.textSelection` 可拖选”。
- 缺口：校准卡是新的 SwiftUI 视图，必须自己嵌入 `SelectableBodyTopReader`（或在滚动时用 `.container` role）把正文顶边回传；正文若可滚动，还要把边界退到滚动区顶边。设计没有提这件事，也没有提“原句区域”是否属于可拖拽区。按现状直接加 `.textSelection`，鼠标事件会先被 `WindowDragCatcher` 吃掉，拖选不生效，A8 会失败。
- 结论：**不成立**。修复见 B-05。

### 3.11 设置变更 / 缓存 / revision

- 操作前：校准缓存中有句子 A 的结果；`configurationGeneration = N`。
- 操作：修改模型列表或超时；随后立即输入英文句 B。
- 现状：`SettingsStore.llmModels` 的 didSet 调 `onTranslationSettingsChanged`（Settings.swift:336-341），`applyTranslationSettings` 先 `configurationGeneration &+= 1`，再在 `configurationTask` 中等待 `previousConfiguration` 后调用 `coordinator.reconfigure(... revision:)`（App.swift:346-377）。`translate` 请求在发起前等待 `configurationReady(configuration)`（App.swift:664-665）。
- 设计：4.4 说“校准协调器一并 reconfigure/清缓存”，5.2 的 `calibrateThrowing(_:revision:)` 有 revision 参数，但 4.2 的执行流程没有说校准请求也要等待 `configurationReady`；也没有说校准用的 `LLMModelRouter` 实例由谁创建、`replaceModels`/`setFallbackTimeout` 在哪里调用。
- 风险：若校准请求在 reconfigure 之前以新 revision 发起，`CalibrationCoordinator` 的 `expected == configurationRevision` 会失败并抛 `CancellationError`，表现为“改了设置后第一句英文没有任何反馈”；若以旧 revision 发起，则可能用旧模型配置，结果仍被 `acceptCalibrationResult` 的 generation 校验丢弃，同样静默。
- 结论：**契约不足**。修复见 B-08；缓存失效的依赖关系见 D-08。

### 3.12 缓存命中 / 同句重打

- 设计 4.1 场景 3：同句删字重打 → “InputCoordinator 句子去重 + 校准缓存命中 → 不重发请求”。
- 现状：`observe` 在抽出的句子变化时会清空 `lastSentence`/`lastSentenceKey`（Input.swift:166-173）；删字重打期间抽出的句子会变化，去重状态被重置，因此**去重并不能吸收重打**，只能靠 `CalibrationCoordinator` 的 64 条缓存。
- 结论：**结论仍成立（不重发），但归因写错**；应在正文中改成“缓存命中”，不要把去重算作保障。非阻塞，列入 D-08 的说明。

### 3.13 钉住卡与单活动卡

- 设计 D-C7/4.3：同一时刻只有一张活动卡；钉住的翻译卡与钉住的校准卡可并存。
- 现状：`hideRealtime` 过滤 `isRealtime && !detached`；`detached = contentPinned || (isRealtime && isPinned)`（Overlay.swift:834-835、1449-1451）。新卡 `show` 在创建前调用 `hideRealtime()`（1025），所以未钉住的旧实时卡会被顶掉；钉住卡保留。
- 结论：**成立**。但“开关关闭/失败时钉住的校准卡是否保留”没有定义；按现有 `hideUnpinned` 语义会保留（1382-1384），与 4.1“开关关闭 → 清空”不完全一致。列入 B-03 的边界。

## 4. 发现清单

### 4.1 阻塞缺陷

#### B-01 校准路由与翻译优先规则互相矛盾，非中文源语言会过度触发

- **位置**：文档 4.1 规则表（119-124 行）、4.1 机制段（126 行）、D-C2（94 行）、D-C8（100 行）、A4（304 行）、11 章“已接受限制”（323 行）；代码 `Sources/Pico/Models.swift:319-331`、`Sources/Pico/Models.swift:194-204`。
- **依据**：4.1 把 `CalibrationState` 的语言过滤定义为“无 Han 且含 Latin”；规则表第三行又要求“句子无 Han 且含 Latin，源语言检测通过（源语言=英/法/德/西）→ 翻译（现状不变）”。`LanguageTextDetector.contains` 对 `.english/.french/.german/.spanish` 都只检查 Latin；对 `.japanese` 接受 Kana 或 Han；对 `.korean` 接受 Hangul；对 `.russian` 接受 Cyrillic。因此：
  - 源语言=英/法/德/西：任何英文句同时满足翻译检测和“无 Han 且含 Latin”，两路都会接受；
  - 源语言=日/韩/俄：Kana/Hangul/Cyrillic + Latin 的混排句同时满足翻译检测和“无 Han 且含 Latin”，两路都会接受；
  - 只有源语言=中文时，“无 Han 且含 Latin”才等价于“源语言检测不通过”。
  如果按 4.1“同时喂两路”，源=英时校准仍会触发，A4“源=英时英文句走翻译，不出校准卡”不成立，D-C2 的“源语言设为英文时校准自然不触发”也不成立；如果按规则表只走翻译，则 `CalibrationState` 的 Latin 过滤器与规则表冲突。设计没有指定“唯一权威路由判定”，两个独立过滤器可以给出不同答案。
- **影响**：源=英/法/德/西用户会得到校准卡（与已确认的“翻译优先”和 A4 冲突）；源=日/韩/俄的混排句可能同时发翻译与校准请求，出现双请求、双卡竞争，由结果到达顺序决定哪张卡最终留下，违背“单活动卡”和“零行为变化”。
- **是否阻塞**：是。
- **修复方向**：把 4.1 的纯函数定义为**唯一权威路由**：输入（句子文本、源语言、开关），输出 `.translate` / `.calibrate` / `nil`；`CalibrationState` 只接受路由为 `.calibrate` 的句子（或 `update` 接收路由参数），不能自己再做一遍“无 Han 且含 Latin”。规则表补齐源=日/韩/俄的行；A4 增加源=日/韩/俄/法/德的用例；并明确“校准只接管翻译路由不接受的 Latin 句”。

#### B-02 InputCoordinator 的源语言硬过滤没有改，校准路径不会触发

- **位置**：文档 2 章“语言过滤丢弃点”（45 行）、改造影响表 `InputCoordinator` 行（59 行）、4.1 机制段（126 行）；代码 `Sources/Pico/Input.swift:196`、`Sources/Pico/App.swift:234-236`。
- **依据**：`InputCoordinator.emit` 在调用 `onSentence` 之前有：
  ```swift
  guard !sentence.isEmpty, detector.contains(sentence, language: sourceLanguage) else { ... return }
  ```
  `InputCoordinator.sourceLanguage` 由 `applyTranslationSettings` 设为 `settings.sourceLanguage`（App.swift:358）。默认源语言中文时，纯英文句在这一步就被丢弃，`onSentence` 不会触发，`AppState` 根本没有机会路由。设计把丢弃点归到 `RealtimeTranslationState.update`，但那是第二道过滤；只改 `RealtimeTranslationState`/新增 `CalibrationState` 不能把英文句送到 `onSentence`。
- **影响**：按 v1.1 的影响表实现（“发射时携带路由标记，时机机制不变”），校准功能完全不工作。A2/A3/A5/A7 都会失败。
- **是否阻塞**：是。
- **修复方向**：明确 `InputCoordinator` 的改造不止“加路由标记”：
  - 增加 `calibrationEnabled`（或注入路由策略闭包），把 `emit` 的源语言 guard 替换为“路由函数返回非 nil 才发射”；
  - `onSentence` 回调增加路由参数（或拆成 `onTranslationSentence`/`onCalibrationSentence`），同步修改 `AppState` 与全部测试闭包；
  - 开关关闭时路由函数对英文返回 nil，保持 A1 的“英文句无任何动作”；
  - 说明为什么不需要第二个 `InputCoordinator` 实例：单实例可以复用防抖、时机、会话、排除应用、空文本/失焦 reset；两个实例会引入双份防抖、双份 `onEmpty`、双份诊断，并需要同步 `isEnabled`/`delay`/`timing`/`excludedBundleIDs`，反而增加状态分裂。若选择第二个实例，必须把生命周期和 `onEmpty` 去重写清楚。

#### B-03 校准状态与展示的失效路径缺失：英文续写旧卡残留，空字段/失焦/暂停/设置变更未接

- **位置**：文档 4.1 状态转换表（128-136 行）、组合约束推演（140-143 行）；代码 `Sources/Pico/App.swift:213-216`（失焦）、`237-240`（onEmpty）、`622-637`（invalidateRealtime/clearRealtimePresentation）、`458-481`（pause）、`346-377`（设置变更）；`Sources/Pico/Overlay.swift:1449-1451`（hideRealtime）。
- **依据**：
  1. `realtime.update` 对“英文 A → 英文 B”返回 false（两次都是 `sentence=nil`，session 未变），不会触发 `clearRealtimePresentation`；设计没有为 `CalibrationState.update` 返回 true 定义对应的清卡动作，旧校准卡会保留到新结果返回。
  2. `onEmpty`、`onFocusChanged`、`toggle()`、`applyTranslationSettings` 都只调用 `invalidateRealtime`/`realtime.invalidate`，没有 `CalibrationState.invalidate` 或 `CalibrationCoordinator.cancel`。清空字段后，之前发出的校准请求仍可能通过 `CalibrationState.accepts`，在空字段上出卡；失焦/暂停/设置变更同理。
  3. 设计 4.1 写“复用既有失效路径”，但既有路径不清楚：`invalidateRealtime` 只清 `realtime`，`clearRealtimePresentation` 只清翻译的 failure/speech/coordinator。校准需要自己的 `invalidate`/`cancel`/`clearFailure`/`hide`。
  4. 开关关闭时 `applyTranslationSettings` 的 `overlay.hideUnpinned` 会保留 `contentPinned` 的钉住校准卡；4.1 写“清空”，两者语义不一致，需要明确钉住卡是否保留。
- **影响**：用户继续改英文时看到上一条句子的旧判定/回译（最长约 LLM 延迟 + 450ms），可能误以为新句已被校准；清空/切窗口/暂停后仍可能弹出旧句校准卡；钉住卡行为不确定。
- **是否阻塞**：是。
- **修复方向**：新增 `clearCalibrationPresentation()`（清校准 failure、取消 `CalibrationCoordinator`、`overlay.hideRealtime()` 或按内容类型隐藏校准卡）；在 `CalibrationState.update` 返回 true 时调用；把 `CalibrationState.invalidate` 接入 `invalidateRealtime`（覆盖 onEmpty/失焦/暂停/设置变更/授权丢失）；明确钉住校准卡在开关关闭/暂停时的保留策略；状态表补 `showing + 新句 → 清旧卡 → pending` 与 `showing/pending + 空/失焦/暂停/设置 → 清空/取消`；A5 增加这些场景。

#### B-04 校准卡的量高与滚动机制不成立，会破坏“面板高度不短于实测文本”的既有约束

- **位置**：文档 4.3 “负载与分流”（192 行）、7 章出卡延迟/兼容性（271、276 行）；代码 `Sources/Pico/Overlay.swift:1076-1102`（installContent）、`1108-1111`（cardHeightLimit）、`1115-1127`（chromeHeight）、`1459-1511`（relayout，尤其 1468-1471）、`193-267`（OverlaySizing）；测试 `Tests/PicoTests/OverlayCoordinatorRenderingTests.swift:52-74`。
- **依据**：现有翻译卡的高度链是“`OverlaySizing.textHeight` 算自然文本高度 + chrome → `OverlaySizing.plan` 决定是否滚动和 `textHeightLimit`/`cardHeight` → `entry.plannedCardHeight` → `relayout` 取 `max(fitting.height, plannedCardHeight)`”。代码注释和回归测试明确说 `NSHostingView.fittingSize` 上屏后会塌缩（279 字符译文只报 110 点），所以不能只靠 fittingSize。设计对校准卡说“不做纯文本量高，依赖 NSHostingView fittingSize”，同时又说“面板高度沿用 max(fittingSize, 预算高度)”，但没有定义：
  - 校准卡的“自然内容高度”如何测量（issues 列表、回译、原句、头部）；
  - `plannedCardHeight`/`textHeightLimit` 由谁计算，`cardHeightLimit`（240/460/0.6 屏）如何参与；
  - 长 issues 列表何时进入滚动，滚动区顶边在哪里；
  - 校准卡头部（徽标 + 标题 + 按钮）的 chrome 高度如何测量，不能直接复用翻译卡的 `chromeHeight()`。
  如果校准卡没有 `plannedCardHeight`，`relayout` 只剩 `fitting.height`，正是已知会塌缩的值；面板可能比内容矮，卡片画到面板外并压住输入行。
- **影响**：长问题列表/长回译时卡片高度错误、覆盖输入框、滚动条不出现或出现但面板高度不对；A8“拖动缩放”无法实现；违反既有“面板不得矮于实测文本”的约束。
- **是否阻塞**：是。
- **修复方向**：为校准卡定义与翻译卡同构的尺寸计划：
  - 用离屏 `measurePanel` + `NSHostingView`（先不套滚动，或给定一个足够大的临时高度）测自然内容高度，或用 `OverlaySizing` 的 TextKit 思路对纯文本部分测量后再加列表的逐条估算；
  - 用 `OverlaySizing.plan(naturalCardHeight:maxCardHeight:chromeHeight:)` 得到 `textHeightLimit` 与 `cardHeight`，写入 `entry.plannedCardHeight`；
  - 用校准卡自己的 chrome 测量（头部高度 + padding），不要复用翻译卡的 `chromeHeight()`；
  - 滚动时正文（原句 + 回译 + issues）在一个 ScrollView 内，复制/关闭/钉住按钮固定；补一条“面板高度 ≥ 实测内容高度”的回归测试（对应现有 `testCardPanelIsNeverShorterThanItsMeasuredText`）。

#### B-05 校准卡交互复用被高估：正文顶边、拖选、拖拽、缩放、视图类型与刷新路径均无契约

- **位置**：文档 4.3 两模式对照表“布局/隐藏”（174 行）、交互段（194 行）、改造影响表 `OverlayCoordinator/Entry` 行（62 行）；代码 `Sources/Pico/Overlay.swift:12-128`（WindowDragCatcher）、`358-613`（TranslationOverlayView）、`484-498`（catcher/overlay）、`529-553`（textBody）、`635-649`（SelectableBodyTopReader）、`919-930`（selectedService 重建）、`980-986`（refreshAppearance）、`1150-1196`（makeView）、`1256-1322`（mouse/bodyEntry/copySelection）；测试 `Tests/PicoTests/OverlayFollowingTests.swift:78`、`OverlayServiceSwitchingTests.swift:135、191-206`、`OverlaySelectionTests.swift:150-165`。
- **依据**：设计说“布局/隐藏、跟随光标、输入框避让、自动隐藏、悬停暂停、拖动缩放完全一致（按 origin 驱动，与内容形态无关）”。但真正驱动这些行为的不是 origin，而是视图/协调器中的具体实现：
  - 拖拽与悬停：`TranslationOverlayView` 在 `.overlay` 里挂 `WindowDragCatcherRepresentable`，并把 `onHoverChange` 转给协调器；
  - 拖选：`SelectableBodyTopReader` 回传正文顶边，`WindowDragCatcherView.hitTest` 在该边界以下放行给 SwiftUI 文本选择层；`bodyEntry`/`copySelection` 依赖 `selectableBodyTop`；
  - 缩放：`resizeHandle` 只在 `textHeightLimit != nil` 时出现，`onResize`/`onResizeEnd` 驱动协调器改面板高度；
  - 视图类型：`makeView` 返回 `TranslationOverlayView`，`hostingView` 返回 `NSHostingView<TranslationOverlayView>`；`selectedService.didSet`/`refreshAppearance` 用 `entry.text` 重建所有卡的 rootView；测试里有强制转换 `NSHostingView<TranslationOverlayView>`；
  - `Entry` 负载改为枚举后，`show` 的更新分支（`existing.text = text`）、`cardContents`、`installContent` 的 `measuredText`、`finishRetranslation` 都需要按类型分支。
  设计只写了“makeView/installContent 分流”，没有写这些调用点，也没有说 `CalibrationCardView` 要自己实现/复用 bodyTop 回传、hover 转发、resize handle、pin/copy/close、feedback、宽度 340…600。按现状直接加 `.textSelection`，`selectableBodyTop` 为 nil，`WindowDragCatcherView.hitTest` 会把整卡（除头部）当作拖拽区，正文收不到鼠标事件，拖选不生效；`bodyEntry` 也找不到可选中卡。
- **影响**：A8 的“拖动、钉住、复制、拖选”行为与翻译卡不一致；长卡滚动/缩放无法工作；`Entry` 改枚举会破坏既有 overlay 测试的强制类型转换，或迫使实现者重做视图结构；校准卡可能复制错误内容（如果复用 `entry.text` 而不是 `corrected`）。
- **是否阻塞**：是。
- **修复方向**：
  - 抽出共享的卡片外壳（标题栏、pin/copy/close、WindowDragCatcher、hover、feedback、宽度/padding），校准卡只提供正文内容；或至少在 5.2 明确 `CalibrationCardView` 必须实现/复用的交互契约；
  - 明确正文顶边回传：短卡用原句之后的边界，滚动卡用 ScrollView 容器顶边（对应 `SelectableBodyTopReader` 的 `.translation`/`.container` 角色）；
  - 说明 `makeView` 如何按 payload 分流而保持翻译卡仍是 `TranslationOverlayView`（避免破坏既有测试的 `NSHostingView<TranslationOverlayView>` 转换）；或列出需要同步修改的测试；
  - `Entry` 的按类型更新/查找（同 key 同 origin 下翻译卡与校准卡不应互相更新），`selectedService`/`refreshAppearance`/`finishRetranslation`/`cardContents` 的分支要写清；
  - 校准卡复制按钮明确取 `corrected`，不是 `entry.text`。

#### B-06 解码宽容规则会把 minor/major 降为 good，掩盖真实问题

- **位置**：文档 5.1 “解码宽容规则”（236 行）、字段表 `issues[].quote`/`kind`/`fix`（231-234 行）、A6（306 行）、4.2 执行流程（151 行）；代码 `Sources/Pico/LLMTranslation.swift:680-700`（现有解码只服务纯文本）。
- **依据**：5.1 写“`issues`/`corrected` 缺失时按 good+空列表兜底不失败（模型判 good 常省略），`verdict`/`back_translation_zh` 缺失才失败”。这条规则没有区分 `verdict`：
  - `verdict=minor/major`、`issues` 缺失 → 被改成 `good` + 空列表，卡片显示“✓ 表达到位”，真实问题被隐藏；
  - `verdict=major`、`corrected` 缺失 → 同样降为 good，复制按钮复制什么也未定义（原文？空？修正句不可得）；
  - `issues` 全部因 `quote` 不匹配被丢弃 → 可能是 `major` 红徽标 + “未发现问题”的空列表，语义自相矛盾。
  这与 D-C4“解码失败计为该模型失败，失败不冒充校准结果”以及 A6“合法兜底通过、非法计失败”的目标冲突。模型“判 good 时省略 issues”是合理的宽容场景，但不能推广到 minor/major。
- **影响**：最坏情况是把有语法/表意问题的句子显示为“表达到位”，直接破坏功能信任；`corrected` 缺失时复制按钮行为不确定；A6 的“缺 issues”用例会把错误行为固化成预期。
- **是否阻塞**：是。
- **修复方向**：把宽容规则改为：
  - `verdict` 缺失 → 视为解码失败（或仅在 `issues` 为空时允许推断 good，需明确）；
  - `verdict == good` 且 `issues`/`corrected` 缺失 → `good` + 空列表 + `corrected=原句`（明确兜底）；
  - `verdict == minor/major` 且 `issues` 缺失 → 保留 verdict，列表显示“模型未提供具体问题”，或计为 malformed 参与 failover；不得改 verdict；
  - `corrected` 缺失时：good 用原句，minor/major 视为 malformed 或禁用复制并提示；
  - 所有 issue 被丢弃时，若 verdict 非 good，保留 verdict 并在列表显示“问题定位失败”，不能显示“未发现问题”；
  - A6 增加 `minor/major + 缺 issues`、`major + 缺 corrected`、`全部 quote 不匹配` 三组用例。

#### B-07 “回译”回译的是原句还是修正句没有定义，核心语义可被实现者猜错

- **位置**：文档 1 章目标（24-26 行）、4.2 提示词要点（149 行）、5.1 字段表 `back_translation_zh`（229 行）、4.3 卡片结构（183 行）；代码无对应实现（新增）。
- **依据**：需求是“同时显示中文（回译），用于中英对照验证是否表达了本意”。`back_translation_zh` 的说明是“这句话实际表达的中文意思”，`4.2` 只说“`reason_zh` 用中文”，没有说回译对象是**原始英文句**还是**修正后的英文句**。如果模型回译的是 `corrected`，那么原句的错误会被“修正”掉，用户看到的中文是模型想让句子表达的意思，而不是句子实际表达的意思，核心验证目的失效。尤其 `verdict=major` 时，回译原句可能是别扭甚至不通的中文，但这正是用户需要看到的“实际效果”。
- **影响**：功能最核心的“中英对照验证本意”可能给出误导性中文；不同模型/提示词下行为不一致，A2 无法稳定判定。
- **是否阻塞**：是（提示词契约与 5.1 字段语义）。
- **修复方向**：在 4.2 提示词要点和 5.1 字段说明中明确：
  - `back_translation_zh` 必须回译**原始英文句**的字面意思，即使原句有语法错误；不得按 `corrected` 回译；
  - `corrected` 是独立的修正结果，卡内单独展示（见 D-04）；
  - 给一个 `major` 原句 + 回译的示例，写进 5.1 或 A2；
  - 若模型无法回译（原句完全不可解析），要求返回“无法回译：……”而不是编造通顺中文。

#### B-08 校准 Router/Coordinator 的实例归属、配置传播与 readiness 屏障未定义

- **位置**：文档 4.2 “职责”（147 行）、5.2 模块契约（240-246 行）、4.4 “变更传播”（200 行）、8 章约束（287 行）；代码 `Sources/Pico/LLMTranslation.swift:313-322`（Router 初始化）、`Sources/Pico/Models.swift:589-622`（TranslationService 只在选中后端时通过 modelFactory 创建 Router）、`Sources/Pico/App.swift:378-382`（configurationReady）、`664-665`（translate 的 readiness 等待）。
- **依据**：
  - 现有 `LLMModelRouter` 由 `TranslationService` 的 `modelFactory` 在 `configure` 时创建，只有 `translationBackend == .languageModel` 时才会被选中；校准要求“固定走自定义模型列表”，与 `translationBackend` 无关，因此不能直接复用 `TranslationService.selected`。
  - 5.2 只说 `CalibrationCoordinator.calibrateThrowing` 调用 `LLMModelRouter.calibrate`，没有说 Router 实例由谁创建、AppState 初始化时从哪里拿 `settings.llmModels`/`llmFallbackTimeout`、模型列表/超时变化时如何 `replaceModels`/`setFallbackTimeout`、`CalibrationCoordinator` 的 `reconfigure` 签名是什么。
  - 4.4 说“校准协调器一并 reconfigure/清缓存”，但 `applyTranslationSettings` 的 `configurationTask` 只 await `coordinator.reconfigure` 和 `clipboardCoordinator.reconfigure`（App.swift:369-376）；校准的 reconfigure 加在哪里、是否阻塞 readiness，没有写。
  - 4.2 的执行流程从“遍历启用模型”开始，没有 `configurationReady(configuration)` 的等待；翻译路径有（App.swift:665）。设置变更后立即输入英文，校准请求可能因 revision 不匹配抛 `CancellationError` 被静默丢弃，或使用旧配置。
  - `CalibrationVerdict` 是跨 actor 返回的值类型，5.1/6 章没有声明 `Sendable`；`CalibrationCoordinator` 是 actor，Router 也是 actor，返回值必须可跨隔离域。
- **影响**：实现者必须自行决定模块结构；设置变更后第一句英文可能无反馈；模型配置/超时变更可能与校准使用的 Router 不同步；缓存清空时机不确定。
- **是否阻塞**：是。
- **修复方向**：
  - 明确 `CalibrationCoordinator` 持有一个独立的 `LLMModelRouter`（或一个专用的 `TranslationService` 实例，backend 固定 `.languageModel`），由 `AppState` 在 init 时用 `settings.llmModels`/`llmFallbackTimeout` 构造；
  - 定义 `reconfigure(models:timeout:revision:)` 或复用 Router 的 `replaceModels`/`setFallbackTimeout`，并放进 `applyTranslationSettings` 的 `configurationTask`；
  - 校准请求发起前 `guard await configurationReady(configuration)`（与 `translate` 相同），并在 `acceptCalibrationResult` 检查 `configurationGeneration` 与 `enabled`；
  - `CalibrationVerdict` 声明 `Sendable`（如含数组/枚举也满足），在 5.1/6 章写明；
  - 5.2 列出 `CalibrationCoordinator` 的 `cancel`/`clearCache`/`reconfigure` 契约，而不只是“镜像”。

#### B-09 失败提示契约不足：标题、backend 参数、清除时机与旧卡互斥都没有定义

- **位置**：文档 2 章改造影响表 `TranslationFailureMessage` 行（66 行）、4.2 异常表（158 行）、5.2 错误处理表（252 行）；代码 `Sources/Pico/App.swift:928-946`（clearFailure/presentFailure）、`1013-1045`（TranslationFailureNotice）、`Sources/Pico/Models.swift:626-653`（TranslationFailureMessage）。
- **依据**：
  - `presentFailure` 的签名是 `(_ error: any Error, backend: TranslationBackend, origin: OverlayOrigin, key: String, session: InputSessionID)`；校准时没有“翻译后端”语义，传 `settings.translationBackend` 会让 Web 错误文案带上不相关的后端名，传 `.languageModel` 又是硬编码。
  - `TranslationFailureNotice.show` 的标题只有“剪贴板翻译/实时翻译”两种（App.swift:1020-1022），没有“英文校准”；A7 要求的“独立失败提示”在 UI 上会显示成“实时翻译”。
  - `TranslationFailureMessage.text` 对 `LLMTranslationError` 的默认文案是“语言模型翻译失败”；校准失败会显示“翻译失败”，与功能语义不符。
  - 设计没有定义“校准请求开始/成功时清除校准失败”的时机。翻译路径在 `translate()` 开头调用 `clearFailure(realtime: true)`（App.swift:647）；校准路径如果不清，旧的失败提示可能与新卡并存 5 秒。
  - `presentFailure` 内部 `overlay.hideRealtime()` 会移除未钉住的旧实时卡，但钉住的旧校准卡会保留；设计没有说明这是否符合“失败时不出卡”。
  - 校准失败与翻译失败共用 `realtimeFailure` 槽，二者会互相覆盖；菜单栏 `MenuBarMenu` 也把二者都当“实时翻译失败”显示。
- **影响**：A7 的“独立失败提示”不成立；用户看到错误标题/错误文案；失败提示与新卡或旧钉住卡并存；翻译失败与校准失败互相覆盖，排障困难。
- **是否阻塞**：是。
- **修复方向**：
  - 为校准定义独立的失败呈现通道（新 `TranslationFailureKind`/`CalibrationFailureNotice`，或给 `TranslationFailureMessage`/`TranslationFailureNotice` 加 `kind` 参数），标题“英文校准”，文案“校准失败/未配置模型”；
  - 明确 `presentFailure` 对校准卡的隐藏范围（未钉住全部隐藏；钉住卡保留但需在文案/行为上说明）；
  - 校准请求开始时清校准失败，成功时清校准失败；不要依赖翻译的 `clearFailure(realtime:)`；
  - 菜单栏显示区分“翻译失败/校准失败”；
  - A7 增加“旧校准卡在途失败”“钉住翻译卡在场时校准失败”“翻译失败后校准成功”三个场景。

### 4.2 非阻塞缺陷

#### D-01 设置组可见性与模型配置入口未定义，默认后端下可能看不到开关/无法配置模型

- **位置**：文档 4.4（199 行）；代码 `Sources/Pico/SettingsUI.swift:762-848`，尤其 846-848：
  ```swift
  if settings.translationBackend == .languageModel {
      modelSettingsSection
  }
  ```
- **依据**：翻译页的模型设置组只在翻译后端为 `.languageModel` 时显示；默认后端是 `.local`（Settings.swift:492）。设计说“「翻译」页新增独立设置组‘英文输入校准’……开关开启但无可用模型时，设置组内直接提示‘未配置模型’”。如果实现者把新组放在模型设置组附近/条件内，默认后端下用户看不到开关；如果放在条件外，用户看到“未配置模型”却没有模型配置入口（模型设置组仍隐藏），只能切翻译后端才能配置，这会改变翻译行为。
- **影响**：开关不可发现或配置路径断裂；A1/A7 手测可能因入口问题无法执行。
- **是否阻塞**：否（易修，但影响可用性验收）。
- **修复方向**：在 4.4 明确新组放在 `translationBackend` 条件之外；模型设置组在“校准开关开启或后端为语言模型”时可见，或在提示旁提供“配置模型”入口；补一条设置页手测。

#### D-02 “英文校准”实际会接管所有 Latin 脚本文本，法/德/西/URL/代码片段都会被当英文

- **位置**：文档 4.1 规则表（122 行）、4.4 设置文案（199 行）；代码 `Sources/Pico/Models.swift:357-361`（`isLatin` 覆盖 Latin-1 Supplement/Extended）。
- **依据**：规则是“无 Han 且含 Latin”，`isLatin` 不只匹配英文，也匹配法/德/西语的重音字符；URL、代码标识符、命令行片段也含 Latin。源语言中文时，输入 `Je suis allé au marché.` 会走校准，卡片标题“英文校准”，提示词按英文审校，模型可能把法语改写成英文。设计没有说明这是“Latin 脚本校准”还是只针对英文。
- **影响**：非英文 Latin 文本得到不相关的“英文修正”；URL/代码片段可能被误判；用户对“英文校准”的边界产生误解。
- **是否阻塞**：否；但应在范围/限制中明确。
- **修复方向**：二选一并在正文写清：接受“Latin 脚本句都校准”（改文案/范围说明，A4 加法语用例），或加一个轻量英文判定（例如至少包含常见英文功能词/空格分词/字母比例），不满足则不触发或标注“非英文，仅供参考”。

#### D-03 Claude thinking 模式与 2048 max_tokens、issues 数量无上限，长结果可能被截断

- **位置**：文档 4.2（147 行）、5.1（213-234 行）；代码 `Sources/Pico/LLMTranslation.swift:660-678`（Claude `max_tokens: 2048`、`thinking.budget_tokens: 1024`）。
- **依据**：校准复用现有 encode 路径与 thinking 模式；Claude 在 `.thinking` 时 `max_tokens=2048`，其中 1024 是 thinking budget，留给 JSON 正文的预算约 1024 tokens。`issues` 没有条数上限，长句/多问题时可超过；OpenAI 兼容端点也没有显式输出上限。截断会表现为 JSON 不合法 → `malformedCalibration` → failover，最终可能全模型失败。
- **影响**：长句/多问题场景校准失败率上升；failover 成本增加；A6 的短 fixture 测不出。
- **是否阻塞**：否；但应在 R-2/A6 中覆盖。
- **修复方向**：提示词要求 issues 最多 N 条（如 6 条，按严重度排序，其余合并到 `corrected`）；校准请求可考虑关闭 thinking 或提高 `max_tokens`（如 4096），并在 A6 加一条长 JSON/接近上限的 fixture。

#### D-04 卡片不展示 corrected 全句，只提供复制按钮

- **位置**：文档 4.3 卡片结构（178-189 行）、主操作表（171 行）。

- **是否阻塞**：否。
- **修复方向**：在卡片内增加“修正后”区块（可折叠/最多 N 行，超出滚动），复制按钮复制该区块；或在问题列表后显示 `corrected` 全文。

#### D-06 A2 写“约 450ms 后校准卡出现”，与第 7 章 2–6s 冲突

#### D-07 提示词版本管理交代不足，7 章“记录于 5.1/4.2”与实际内容不符

- **位置**：文档 7 章已知限制（279 行）、8 章约束（288 行）、4.2 提示词要点（149 行）、5.1（206-236 行）。

#### D-08 缓存失效依赖未明说的 didSet 与配置路径，需补断言

- **位置**：文档 6 章（264 行）、4.4（200 行）、5.2（244 行）；代码 `Sources/Pico/Settings.swift:318-352`、`Sources/Pico/App.swift:346-377`。
- **依据**：缓存 key 只有原句文本，正确性依赖“所有影响校准结果的配置变化都经过 `applyTranslationSettings` 并清空缓存”。设计没有明说 `calibrationEnabled` 的 didSet 要调用 `onTranslationSettingsChanged`；如果只写 `@Published var calibrationEnabled` 而不触发回调，开关切换不会即时清状态/取消在途。模型列表/超时变化已有回调，但校准协调器的 reconfigure 需要显式接入。提示词是代码常量，进程内不会变，因此不纳入 key 在当前版本可接受，但前提要写明。
- **影响**：开关切换后旧卡/旧请求残留；模型配置变化后缓存可能返回旧模型结果；实现者可能漏接 didSet。
- **是否阻塞**：否；但属于“实现者会做错”的契约缺口。
- **修复方向**：在 4.4 明确 `calibrationEnabled` 的 didSet 走 `onTranslationSettingsChanged`（或在 `applyTranslationSettings` 中读取并比较）；在 6 章写明“key 不含 revision 的前提是 reconfigure 同步清空缓存，且提示词为不可配置常量”；补 SettingsStore 单测（开关变更触发回调）与 CalibrationCoordinator 单测（模型列表变化后缓存清空）。

#### D-09 诊断信息与 300 字符截断：诊断报告缺开关字段，长句会被截断后校准

- **位置**：文档 4.4 诊断（202 行）、A9（309 行）；代码 `Sources/Pico/App.swift:491-527`（DiagnosticsSnapshot 未含 calibrationEnabled）、`Sources/Pico/Models.swift:104-119`（`SentenceExtractor.extractSentence(maxLength: 300)` 截取末尾 300 字符）。
- **依据**：
  - “报告问题”生成的诊断快照包含 enabled/timing/speed/language/backend/modelCount/uiLanguage/clipboard 等，但没有校准开关；支持排障时无法判断用户是否开启校准。
  - `SentenceExtractor` 对超过 300 字符的句子只保留末尾 300 字符（`text[range].count > maxLength` 时从 upperBound 回退），校准会拿一个可能从词中间截断的句子去判定/回译，`quote` 也只能匹配截断后的文本。用户会看到“原句”不完整、回译不完整。
  - 设计没有定义长句策略（拒绝/提示截断/提高上限/按句号切分）。
- **影响**：长邮件/长句的校准结果误导；诊断报告缺少关键开关状态；A9 只查日志/历史，查不到报告字段。
- **是否阻塞**：否；但长句是目标场景（邮件/文档）。
- **修复方向**：诊断快照增加 `calibrationEnabled`（不含文本）；正文明确长句策略：例如超过 300 字符不自动校准（提示“句子过长，请分段”）或显示“已截断”标记并只对完整句校准；A9 增加“诊断日志/报告不含原句/响应正文/密钥”的断言；`calibration malformed` 日志不得带响应正文。

#### D-10 自动隐藏默认 5 秒对长校准卡偏短

- **位置**：文档 4.3 布局/隐藏（174 行）；代码 `Sources/Pico/Overlay.swift:1352-1380`（`scheduleHide`）、`Sources/Pico/Settings.swift:464-467`（`hideAfter` 默认 5 秒，范围 5–60）。
- **依据**：校准卡内容比翻译卡长（原句 + 回译 + 多条问题 + 修正句），5 秒内很难读完；悬停可暂停，但用户可能正盯着输入框、鼠标不在卡上。设计说“自动隐藏完全一致”，没有讨论是否需要更长的校准默认值或默认钉住。
- **影响**：用户还没读完卡片就消失，核心价值打折；用户可能被迫频繁钉住，增加操作负担（与“零操作”目标冲突）。
- **是否阻塞**：否；建议在 A10 中观察。
- **修复方向**：考虑校准卡默认更长的 `hideAfter`（如 8–10 秒）或“首次出现不自动隐藏，移动鼠标后开始计时”；至少把“5 秒是否足够”列入 A10 的试用观察项，并让用户决定。

#### D-11 既有测试影响清单不完整，A1“原样通过”与回调签名变更冲突

- **位置**：文档 8 章（286 行）、A1（301 行）；测试文件见下。
- **依据**：设计只提到 `SettingsStoreTests` 的 keys 和“既有输入链路测试不可改语义”，但实际会受影响：
  - `InputCoordinatorTimingTests`、`InputPipelineDiagnosticTests`、`CaretTrackingTests`、`FocusedEditableInputTests`、`OverlayFollowingTests` 使用 `onSentence = { text, _, _, _, _ in ... }` 五参数闭包；若回调增加路由参数，这些闭包必须机械修改。A1 的“全部原样通过”在字面上不可能。
  - `OverlayServiceMetadataTests`、`OverlayServiceSwitchingTests`、`OverlayFollowingTests` 强制转换 `NSHostingView<TranslationOverlayView>` 并访问 `.rootView`；若 `makeView` 改为统一 `AnyView`/枚举根视图，这些测试会编译失败或运行时失败。

### 4.3 待决策

#### Q-01 不完整的英文句是否触发校准（默认 `.pause` 会在句子中途出卡）

- **位置**：文档 4.1 场景（115 行）、4.1 机制（126 行）、A2（302 行）；代码 `Sources/Pico/Settings.swift:499-501`（默认 `.pause`）、`Sources/Pico/Input.swift:115-129`（pause 模式只要防抖到期就 emit）、`Sources/Pico/Models.swift:96-129`（`extractSentence` 会抽取光标所在片段，不要求句末标点）。
- **依据**：默认翻译时机是“停顿”，`SentenceExtractor` 会抽取当前片段（不必是完整句）。校准对片段给出 `minor/major` 判定时，用户可能只是还没打完（例如输入 `I have went` 后停顿思考），卡片会显示“✗ 表意有误/缺宾语”之类的假阳性；回译也是片段的中文。设计没有定义“只对完整句校准”还是“片段也校准”，A2 用的是完整句，无法覆盖默认行为。
- **影响**：默认配置下假阳性/噪音显著，用户信任下降；每个片段都可能发一次 LLM 请求，成本上升（R-4 的缓解措施没有覆盖这一点）。这是产品行为选择，不是实现细节。
- **是否阻塞**：是（影响 A2 的核心行为与质量口径）；需要用户决定。
- **修复方向**（供选择）：
  1. 校准支路独立要求句末标点（复用 `SentenceExtractor.isComplete`），翻译仍按用户选择的时机；仍是自动触发，但不会判片段；
  2. 片段也校准，但卡片标注“当前片段，可能未写完”，且不显示 `major` 徽标/不做修正，只做回译；
  3. 增加最小长度/词数阈值（例如至少 3 个英文单词或 12 个字符），低于阈值不触发；
  4. 保持现状，但在设置文案和 A10 中明确风险。
  建议 1 或 2；无论选哪个，都要在 4.1 写清并补 A2 的片段用例。

#### Q-02 拉丁源配置下“翻译优先”与用户的两模式心智冲突，需用户确认

- **位置**：文档 D-C2（94 行）、D-C8（100 行）、规则表第三行（123 行）、A4（304 行）、11 章已接受限制（323 行）；用户确认口径“检测到中文→中译英，检测到英文→校准”。
- **依据**：D-C2 规定“校准只接管会被源语言过滤丢弃的 Latin 句子；翻译路由优先”，因此在源语言=英/法/德/西时英文句走翻译，校准开关即使打开也不会触发。D-C8 又写“语言路由永远自动（中文→翻译、英文→校准候选）”，用户的两模式描述也是“检测到英文就走校准”。两者在拉丁源配置下不能同时成立。11 章把它标为“已接受限制（D-C2 规则使然）”，但用户确认的是“其余决策按推荐”，并未明确确认“源语言=英文时校准永不触发”这个具体子场景。
- **影响**：源语言=英文的用户打开“英文校准”后发现功能不工作；A4 的预期与用户心智冲突；如果未来要让校准优先，会改变翻译行为（零行为变化的前提被破坏）。
- **是否阻塞**：是（需要用户确认口径后才能定 A4 与路由实现）。
- **修复方向**：请用户确认二选一：
  1. 保持 D-C2（翻译优先）：源语言=英/法/德/西时校准不触发；在设置文案/帮助中明确“英文校准仅在源语言不是拉丁语系时生效”，并把 11 章的限制改成“用户已确认”；
  2. 校准优先（仅开关开启时）：源语言=英/法/德/西的英文句也走校准，中文目标翻译暂停/不再自动；这需要修改 D-C2、A4，并说明翻译行为的变化。
  无论哪种，源=日/韩/俄 的行为也要写进规则表（当前只列了“英/法/德/西”）。

#### Q-03 A10 不达标时“降级为显式触发”改变了 D-C1 已确认的自动触发形态

- **位置**：文档 A10（312 行）、R-1（318 行）、D-C1（93 行）。
- **依据**：D-C1 是用户明确确认的“自动触发（防抖），不做划词/快捷键”；A10/R-1 说质量/延迟不达则“降级为显式触发再评估”。显式触发（划词/快捷键）正是 D-C1 否决的备选，不能在质量不达标时由实现者单方面切换。
- **影响**：可能在没有用户确认的情况下改变产品形态；或者团队误以为已有退路而放松 A10 门槛。
- **是否阻塞**：否（只在 A10 失败时触发）；但必须在文档中改为“回到用户决策”，不能作为自动降级路径。
- **修复方向**：A10/R-1 的退路改为“记录未达标证据，回到用户决定：调提示词/换默认模型/改为显式触发/停用”；不预先承诺降级。

### 4.4 待实证

#### E-01 中文输入法组合态是否始终被 `isComposing` 挡住（拼音被当英文的风险）

- **位置**：文档 4.1（115 行“IME 组合中……上游既有守卫，无需新增”）；代码 `Sources/Pico/Input.swift:99-104`、`175-183`（`emit` 再次检查 `!snapshot.isComposing`）。
- **依据**：现有翻译路径中，拼音（Latin）会被源语言中文过滤器丢弃，所以 `isComposing` 误报不会造成翻译请求；校准路径把 Latin 视为合法输入，一旦宿主没有正确报告组合态，拼音串就会被当作英文句发到模型，造成无意义请求、费用和隐私暴露（拼音可能包含用户输入内容）。设计断言“上游已挡”，但没有给宿主证据。
- **影响**：高频中文输入用户可能触发大量校准请求；隐私/成本风险；A1“开关关闭时英文无动作”不受影响，但开关开启后体验可能严重劣化。
- **证据缺口/验证条件**：在微信、备忘录、Chrome、Safari、Obsidian 等宿主中用中文输入法连续输入拼音，观察 `snapshot.isComposing`/AX marked text 与诊断日志；确认组合期间无 `debounce elapsed`/`calibration requested`。若存在宿主不报告，需加启发式（例如拼音无空格/无英文功能词、最小长度、至少一个空格分词）或延迟到提交后再判定。
- **允许承诺的边界**：在证据取得前，不能写“IME 组合已被上游完全挡住”；应在 R 系列中保留该风险。

#### E-02 A10 的质量/延迟门槛需要可判定口径

- **位置**：文档 7 章（272-274 行）、A10（310-312 行）、R-1（318 行）。

- **允许承诺的边界**：在 A10 完成前，只能承诺“功能可用”，不能承诺“质量达标/可发行”。

#### E-03 各提供商 JSON 遵从度不能由 A6 单测代替

## 7. 范围合理性

- **机制是否服务目标**：路由、状态机、独立 coordinator、Router 内校准任务、共享浮窗、设置开关都直接服务“自动英文校准 + 中文回译 + 零翻译回归”的目标；没有发现为填充章节而加入的额外机制。`CalibrationState` 与 `CalibrationCoordinator` 的镜像设计是合理的隔离手段，避免污染翻译缓存/令牌。
- **遗漏的必要保障**：
  - 不完整句/片段判定（Q-01）——直接影响假阳性；
  - 中文 IME 拼音误触发（E-01）——隐私/成本；
  - 非英文 Latin 文本（D-02）；
  - 长句 300 字符截断（D-09）；
  - 输出 token/issue 上限（D-03）；
  - 自动隐藏时长（D-10）；
  - 诊断报告开关字段（D-09）；
  - 失败提示的独立标题/清除（B-09）。
- **是否有过度复杂性**：没有明显过度设计；64 条缓存、代次令牌、单活动卡都是既有机制的合理镜像。若未来要支持多语言/多句，再扩展 `CalibrationState`，当前不需要。
- **风险分级/合同包**：文档元信息只写“设计分级 标准”，没有按 document-standard 的“高风险跨边界/中风险/低风险”说明合同包。该改动涉及外部 LLM 端点（用户文本出站）和浮窗行为，建议至少定为中风险；A4（路由）与 A6（解码）作为合同测试，A6 最好由非实现者按 5.1 schema 编写或使用黄金样例；高风险测试（数据迁移/权限）不适用。此项不阻塞，但应在修订版补一句风险分级与合同产物。

## 8. 结论与实施边界

- **总体结论**：**有条件可实施**。架构方向正确，现有代码的输入/浮窗/LLM 路由能力可以承载；但 v1.1 的 9 项阻塞缺陷必须先修复，2 项产品口径（Q-01、Q-02）必须先由用户确认。修复后可按 8 章顺序（路由/状态机 → LLM 任务 → 卡片 → 设置）实施；卡片可用假数据先行。
- **当前可实施的部分**（在不改变设计的前提下）：无。B-02 使校准主路径不可触发；B-01 使路由不确定；B-04/B-05 使卡片无法按 A8 验收。建议不要以“先搭骨架”为由绕过这些契约，否则后续会返工。
- **修订后需补齐的证据**：E-01（IME）、E-02（A10 口径/试用）、E-03（provider 矩阵）、E-04（长卡真机）。
- **未修改被审文档**：本报告仅为审阅记录；被审文档仍为 v1.1。
- **审阅限制**：本文为独立代码阅读审阅，未运行应用/测试；未核实项见 0.2。没有发现问题不等于用户批准、已实现或已实测。
