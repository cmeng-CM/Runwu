## 1. 总体结论

**有条件可实施。**

v1.2 的修复方向正确，且大部分是实质性修复，不是文字补丁：

- **B-01 闭合**：D-C9 成为唯一路由权威，4.1 源语言矩阵覆盖中文/拉丁源/日韩俄/不命中，明确“两者互斥”，`CalibrationState` 不再独立做脚本过滤。Q-02 的“仅源语言=中文”落到 D-C2/D-C9/A4。
- **B-05 基本闭合**：抽出 `OverlayCardShell`、`Entry.content` 枚举、翻译宿主类型保持不变、bodyTop/hover/resize 由外壳承载；这正面回应了“origin 不继承视图层机制”的问题。
- **B-06 基本闭合**：5.1 的严格校验把 minor/major 的 issues/corrected 设为必需，全 quote 失效判 malformed，good 带 issues 降 minor；不再出现“红徽标 + 未发现问题”。
- **B-07 闭合**：D-C11、4.2 提示词要点、5.1 字段、4.3 卡片文案都明确回译**原句（含错误）**，corrected 单独展示。
- **B-09 基本闭合**：独立 `CalibrationFailureState`/`presentCalibrationFailure`、标题“英文校准失败”、清除时机、不动钉住卡，A7 覆盖全挂/未配置/钉住卡并存。

但**不能据此宣称“9 项阻塞缺陷已闭合、具备实施条件”**。以下仍有残余：

1. **B-02 残余**：`InputCoordinator.emit` 改用 `RouteDecision` 已写明，但 `RouteDecision` 需要 `calibrationEnabled`；v1.2 没有写开关如何传到 `InputCoordinator`，也没有写应用启动时（持久化为 true）如何初始化该开关。`applyCalibrationSettings` 只做 generation/取消/隐藏/清缓存/重配 Router，没有 `input.calibrationEnabled = ...`；`AppState.init` 只走 `applyTranslationSettings`。按字面实现，开关打开后 `InputCoordinator` 仍可能用 false 路由，英文句继续 `.none`。
2. **B-03 残余**：`clearCalibrationPresentation` 与状态表已经写了“新句旧卡立即隐藏”，但触发点不完整：
   - 路由切到 `.none` 时，没有状态机收到句子；`InputCoordinator.emit` 对 `.none` 只保留 `sourceLanguageMismatch` 诊断，是否回调 `onSentence(.none)` 未写。若 `.none` 不送达，旧校准卡/在途请求/失败提示不会被清。
   - 路由从 `.calibrate` 切到 `.translate` 时，翻译状态变化走的是 `clearRealtimePresentation`，不是 `invalidateRealtime`；v1.2 只说 `clearCalibrationPresentation` 接入 `invalidateRealtime`，没有说接入 `clearRealtimePresentation`/`handleInputSnapshot` 的路由切换点。
   - `clearCalibrationPresentation` 只写“隐藏未钉住卡、取消在途请求”，没有写 `CalibrationState.invalidate`；状态表要求 `accepts==false`，但缓存命中可能绕过取消。需要把“取消请求”和“令牌失效”都写实。
3. **B-08 残余**：
   - 4.1 场景 6 说“开关在请求在途时关闭 → `applyTranslationSettings` generation++、取消请求、清缓存、隐藏未钉住卡”，与 4.4 的 `calibrationEnabled didSet → applyCalibrationSettings` 冲突。按 4.1 实现，关校准开关会走翻译的设置失效链，可能取消在途翻译；按 4.4 实现则不会。两条指令必须统一。
   - `applyCalibrationSettings` 的 `generation++` 没有说明是独立的 `calibrationGeneration` 还是共享的 `configurationGeneration`；若共享，开关切换会使翻译请求的 `configurationReady`/`accepts` 失败，违背“翻译行为零改变”。
   - 4.3 的 `acceptCalibrationResult` 仍写“镜像 acceptTranslationResult 的令牌/会话/屏幕处理”，没有明确 `configurationGeneration`、`enabled`、当前 route 的校验；设置变更后迟到结果仍可能在 guard 不足时出卡。
4. **B-04 需澄清**：`CalibrationCardSizing.plan`/`OverlaySizing.plan` 的分段测量方向正确，但 4.3 的“`CalibrationCardSizing.plan` ... 得到 `plannedCardHeight`；`OverlaySizing.plan(...)` 决定滚动阈值；面板高度取 `max(plannedCardHeight, fittingSize)`”没有明确 `plannedCardHeight` 取的是 `plan.cardHeight`（钳制后）还是自然高度。若取自然高度，`max(planned, fitting)` 会突破 `cardHeightLimit`。A8 的“面板高度 ≥ 内容；长卡滚动”对滚动卡也自相矛盾（滚动卡面板本应小于完整内容）。需要把赋值顺序和断言口径写死。
5. **新阻塞 D-C14/A11**：v1.2 新增“超过 300 UTF-16 单元跳过校准”，但 `ExtractedSentence` 只有 `text/range`，`SentenceExtractor` 在超过 `maxLength` 时**直接截掉**（`Models.swift:116-118`），没有 `truncated`/原始长度字段；`maxLength` 还是 `Character` 计数，不是 UTF-16。设计没有说明如何判断“原句超过 300”，按现有 API 无法可靠实现 A11，也无法避免把截断片段送去校准。

因此当前 v1.2 仍是**有条件可实施**：B-01/B-05/B-06/B-07/B-09 可视为闭合；B-02/B-03/B-08 需补残余；B-04 需澄清；D-C14/A11 需补一个输入契约。修订后可按第 8 章顺序实施。

## 4. 新发现问题

### 4.1 新阻塞项

#### N-01 D-C14/A11 的“长句跳过”无法用现有 `ExtractedSentence` 实现，且单位写错

- **位置**：v1.2 D-C14（113 行）、4.2 异常表（195 行）、A11（370 行）、R-6（386 行）、11 章；代码 `Sources/Pico/Models.swift:90-94`（`ExtractedSentence` 只有 `text/range`）、`Sources/Pico/Models.swift:104-119`（`extractSentence` 在超长时直接截断）；`Sources/Pico/Input.swift:184`（`extractSentence` 调用）。
- **依据**：
  - `SentenceExtractor.extractSentence` 的 `maxLength` 默认 300；当 `text[range].count > maxLength` 时，直接把 range 截成末尾 300 个 **Character**（`text[range].count` + `text.index(..., offsetBy: -maxLength)`），返回的 `ExtractedSentence` 没有 `truncated`、`originalLength` 或原始范围起点，AppState/`CalibrationState` 无法知道“原句超过 300”，只能看到已被截断的片段。
  - 设计说“超过 300 **UTF-16 单元**”，但现有实现是 `Character` 计数；对 ASCII 英文两者接近，对 emoji/组合字符不同。A11 的“300 UTF-16 单元”与代码事实不一致。
  - 4.2 只写“句子超过 300 → 不发起请求，记 `calibration skipped reason=tooLong`”，没有写检查发生在 `InputCoordinator`、`CalibrationState` 还是 AppState，也没有写如何从 `ExtractedSentence` 得到原始长度。
- **影响**：A11 无法按设计实现；实现者可能用 `extracted.text.count == 300` 猜测，误杀恰好 300 的句子或漏掉截断句；截断片段仍可能被校准，导致回译/quote/修正句基于半句，违背 D-C14 的目的。
- **是否阻塞**：是（新增阻塞）。
- **修复方向**：二选一并在 5.1/5.2 写清：

#### N-02 B-03 残余：`.none` 路由变化没有送达 AppState，`clearCalibrationPresentation` 的触发点不完整

- **依据**：

  - 用户从英文校准句改成纯数字/表情/西里尔句（源=中文、开关开）时，`RouteDecision` 为 `.none`；翻译状态 `realtime.update` 抽到该句但源语言中文检测失败 → `sentence=nil`，若之前也是 nil（校准卡显示中），`update` 返回 false，不会触发 `clearRealtimePresentation`；`CalibrationState` 也不收句。结果是旧校准卡/在途请求/失败提示继续存在，直到自动隐藏或下一次事件。
